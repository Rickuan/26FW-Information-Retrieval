## 0. 在整條管線中的位置

```
04.warc
 → M1 iter_documents()        Document(doc_num, trec_id, url, kind, text)
 → M2 Preprocessor.process()  [(pos, term), ...]
 → M3 Indexer.build()         index / doc_map / stats        ← 本模組
 → M5 SkipBuilder             skip pointers + AND 查詢
 → M4 IndexWriter             輸出檔案
```

`Indexer.build()` 內部會自呼叫 M1 / M2，M4/M5 不需另行讀 WARC 或斷詞（查詢詞需經同一個 Preprocessor 處理）。

## 2. 與原計畫的差異

| 項目 | 原計畫 | 實作 | 理由 |
|---|---|---|---|
| 內部儲存 | `dict[str, list[Posting]]` | 欄式儲存（見 §3） | 記憶體 −70%；對外仍提供 `Posting` |
| `Posting.positions` | `list[int]` | `array('I')` | 讀取時由 pos 陣列切片產生 |
| `idx.index` | 真正的 dict | 唯讀 `Mapping` view，取值時才組出 `list[Posting]` | 相容原用法；**每次取值是新物件** |
| SPIMI 觸發 | psutil RSS > 1500 MB，每 500 篇 | 累積位置數 ≥ `flush_every`（預設 3,000,000） | Python 釋放記憶體後 RSS 不下降，會不斷誤觸發 |
| partial 格式 | 序列化整個 index | 依詞排序後逐筆 pickle `(term, docs, tfs, pos)` | 才能串流歸併 |
| SPIMI 預設 | 整合於 `build()` | `Indexer(spimi=True)` 選擇性開啟 | 全記憶體僅需 1.1 GB；M5 需隨機存取 |
| SPIMI AC | 200 MB；抽查 5 詞 | 實測 604 MB；全部詞比對 | 200 MB 低於 Python + spaCy + bs4 基本用量 |
| 效能 AC | ≥ 500 docs/s | ≥ 80 docs/s | 上游擷取 + 斷詞約 96 docs/s 為瓶頸 |
| `doc_len` | 「加入索引的 token 總數」 | `len(terms)`，不含被移除的停用詞 | 原說明與 AC 不一致，依 AC |
| 新增介面 | — | `iter_postings`、`get_postings`、`df`、`prefix_search`、`build_trie`、`cleanup` | SPIMI 串流、trie、欄式儲存 |

## 3. 資料結構

**內部儲存**：每個詞一個 `_Columns`（docs / tfs / pos 三個 `array('I')`），讀取時才組回 `Posting` 物件。

**位置規則**（非顯然）
- 標點、附著詞（`'s`）、長度 > 64 的 token：**不佔位置**
- 停用詞（開啟移除時）：**佔位置但不建 postings** → positions 可能跳號（1, 2, 4），但仍嚴格遞增

## 4. 工項與 AC

| Step | 說明 | 關鍵 AC ✅ |
|---|---|---|
| 3-A `add_document` | 模組層級參考實作（原規格）；保留供正確性對照 | `tf == len(positions)`；`doc_num` 嚴格遞增；`doc_len == len(terms)` |
| 3-B `Indexer`（全記憶體） | `build()` 自呼叫 M1 / M2；`get_stats()` 計算彙總 | postings 全域嚴格遞增；`sum(tf) == total_tokens` |
| 3-C SPIMI | 位置數觸發 flush；`heapq.merge` 多路歸併；同詞陣列直接串接 | SPIMI vs 全記憶體全部詞逐筆一致；604 MB < 1,110 MB |
| 3-D 測試 | 單元 + 一致性 + 邊界（空文件、全停用詞） | 空文件 `doc_len == 0`、無 posting；速度 ≥ 80 docs/s |
| 3-E Radix Trie（加分） | `trie.py`；lazy 建立（第一次 `prefix_search` 才觸發）；只存 df | 644,523 詞 / 770,227 節點；`trie.get(t) == idx.df(t)` |
| 3-F 欄式儲存 | `_Columns`（docs / tfs / pos）；`_PostingsView(Mapping)` 維持原 dict 介面 | SHA-1 與參考實作相同；Peak RSS ≤ 50%；M4 輸出時間增加 ≤ 20% |

## 5. 對外介面（供 M4 / M5）

| 介面 | 全記憶體 | SPIMI | 用途 |
|---|---|---|---|
| `iter_postings()` | ✅ | ✅（每次呼叫重讀 merged 檔） | 走訪全部詞：寫檔、建 skip |
| `index[term]` / `get_postings(term)` | ✅ | ❌ | 查特定詞 |
| `df(term)` | ✅ | ❌ | 只需 df 時（不組物件） |
| `prefix_search()` | ✅ 回傳 `(term, postings)` | ⚠️ 回傳 `(term, df)` | 前綴查詢 |
| `doc_map` / `stats` | ✅ | ✅ | metadata |

> **整合指引**：單次 `iter_postings()` 走訪寫出所有產物；全記憶體模式才執行 `SkipBuilder`；結束時呼叫 `idx.cleanup()`。

### 注意事項

1. **`positions` 是 `array('I')`，不是 list**
   - 可以：`for x in p.positions`、`len()`、`", ".join(map(str, p.positions))`、切片
   - 不行：`p.positions == [1, 3]`（永遠 False）、`json.dump`（會失敗）→ 先 `list(p.positions)`
   - M4 round-trip AC（`decode(encode(p)) == original`）：decode 要產生 `array('I')`，或比較時兩邊都轉 list

2. **輸出格式需含 positions**（投影片 p.9）：`term, df: <docID, tf: <pos1, pos2, …>; …>`，另外需產生一詞一行的 dictionary 檔（由 M4 負責）。

3. **查詢詞要先經過同一個 Preprocessor**
   開啟 stem 時，索引裡存的是 `game`；直接查 `"games"` 或 `"Game"` 會查不到。查詢前先用 `pre.process(query)`。

4. **每次取值都是新物件**（兩種模式皆然）
   `idx.index[t]`、`get_postings(t)`、`iter_postings()` 每次都重新組出 `Posting`。
   - 不要用 `is` 比較；要比較內容 `(doc_num, tf, list(positions))`
   - 不要在迴圈中反覆查同一個高頻詞（每次約 9 ms），請存起來重用
   - `idx.index` 是唯讀的，不能 `idx.index[t] = ...`
   - `doc_num` 來自 TREC-ID 尾碼，不重新賦號；Delta encoding 由 M4 負責

5. **M5 的 `PostingWithSkip` 不要複製 positions**
   用 `positions=p.positions` 引用同一個 array，不要 `list(p.positions)`；否則 1,183 萬筆 posting 會再增加數 GB 記憶體。
